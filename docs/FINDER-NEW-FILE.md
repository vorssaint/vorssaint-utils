# Finder New File

An optional feature in Features → Clipboard & Files → New File. Install it in the feature hub, open its section on the Finder settings page, choose the file types and enable the Finder extension in System Settings. The installed feature hub row and the Finder settings section always show the extension's enabled/disabled status and a System Settings action, even when the feature switch is off. An orange warning explains missing enablement; a green check replaces it when enabled. As with the existing system tiling settings, the status refreshes on appearance and app activation. The system query runs off the UI thread, following the permission portal's automation check. No periodic extension polling is used. The feature hub and Finder settings reuse the same Finder extension status component, which follows the existing permission-row visual style without changing the original permission components. The host accesses the shared localization catalog through FeatureStrings; the extension uses the same catalog and the host's exact AppLanguage identifier. No Accessibility or Full Disk Access grant is required just to expose the menu; macOS may request access to protected folders when a file is created.

The menu appears on a supported folder background (including the Desktop) or a single selected item. A selected ordinary folder is the destination; a selected file uses its enclosing folder. Multiple selections and packages are not used as ambiguous destinations. The host revalidates the destination and uses exclusive writes and numbered names. Office and iWork files use bundled blank templates. Settings follow the app language and are included in settings backup.

## Custom documents

Add a custom document in the Finder settings section. Set the menu name, base filename and optional suffix (with or without the leading dot). Choose a regular file as a template, or leave it empty to create a zero-byte file. All entries share one ordered list and can be enabled, disabled, edited and reordered by dragging their handles. Only custom entries can be removed. Built-in entries can use their original content, an imported template or an empty file. The Finder menu follows the same order with no separator. Previous selection and custom preferences are migrated when the unified list is first saved. Existing files are never overwritten; a repeated filename gets a numbered suffix.

Up to 32 custom entries are supported. Each template can be up to 64 MB. The host imports a private copy via the existing PrivateFileStore, so moving or deleting the original template does not affect creation. Templates are stored under the app variant's Application Support directory, not in its signed bundle. Only menu IDs, labels and icon names are shared with the extension. The normal settings backup includes custom entry definitions, not the user's private template contents. After moving settings to another Mac, reselect any missing templates; creation fails rather than silently writing an empty file.

## Security and development

Developer and release builds use the same one-click path. The sandboxed Finder Sync extension opens the containing app without activating it. The host captures the OS-provided Apple event sender audit token while handling the event and checks that the sender's running code matches the exact code-directory hash of the installed embedded extension. Unauthenticated events, including forged external URLs, are rejected; there is no confirmation fallback. The host additionally validates the file kind, directory, feature and extension state, request expiration and per-process replay protection. Successful creation is silent. Write errors are presented in the host.

Only menu presentation data is shared through a dedicated read-only preferences entitlement; it never authorizes file creation. Developer and release variants retain separate identifiers and preference domains. There is no App Group dependency, listener, filesystem crawler or additional helper process.

## Validation before review

- Build with `./build.sh --dev`, run `./build/VorssaintDeveloper --selftest` and `./build.sh --test-suite=utilities`.
- Install with `./build.sh --dev --install` and opt into the feature. The official app should remain untouched.
- Verify on macOS 14 and later: Finder background, Desktop, folder and file selections; repeated names; Office and iWork document opening; language and feature toggles; silent creation with no activation; protected-folder errors.
- With the extension disabled, install and enable the feature: check the orange warning in the feature hub and the Finder settings section. Enable the extension in System Settings, return to the app, and verify the warning changes to a green check while the management button remains. Toggle the extension in System Settings, then return to the app to confirm the state refreshes. Turn off the feature switch and verify the extension management entry remains available. Disable the extension again and confirm the warning returns. Check the other app variant independently.
- Verify local signing, ad-hoc signing and Developer ID signing separately. Launch Services must preserve the extension's sender audit token in the host's open-URL callback. If a genuine menu click is rejected, inspect the host's "rejected unauthenticated Apple event" log; do not loosen the sender check or accept arbitrary URLs.
- Verify an externally constructed create URL cannot create a file, even with a valid payload. Replay the same authenticated request and verify only one file is created.
- Verify custom document addition and removal, editing both built-in and custom items, switching visibility, dragging across both kinds, persistent order after relaunch, blank creation, multi-dot or empty suffix, copied template bytes, same-name collisions, and missing templates. Verify all languages and settings backup metadata. Inline Finder rename remains outside this change.
